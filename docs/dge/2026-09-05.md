## 2. 観点別に見つけた候補（すべて実測で確認）

計測環境: JDK 21 (`OpenJDK 64-Bit Server VM 26.0.2.1`)、`mvn -Dtest=... test`、base `3e991aa`。
一時 probe テストを置いて実行し、確認後に削除した（commit していない）。

| # | 観点 | 候補 | 実測結果 |
|---|---|---|---|
| A | 失敗時 / 運用者 | auto-chain が上限 10 に達すると無音で停止する。**正当な DAG** でも起きる | 13 手の auto 連鎖 → `build()` 成功、`Carta.start()` は例外なし、`currentState=S10`、`isCompleted()=false`、`log().size()=10`。外部入力待ちと区別不能 |
| B | 保守者 / build-time 検証 | V4 (`validateAutoDAG`) が遷移先を `resolveToLeaf()` で解決しないため、複合状態の初期子へ戻る cycle を見逃す | `auto("P1","Processing")` かつ `Processing.initial = P1` で `build()` 成功 → runtime で 10 回空回りして無音停止。branch 経由（`branch("P1", ..., {"loop":"Processing"})`）でも同じ |
| C | 利用者 / event bubbling | `findExternalTransitions()` は最初に external を持つ階層で打ち切るため、親に定義した external 遷移が子から到達不能になる。さらに guard が1つも評価されていないのに `resume()` が `REJECTED` を返す | 子に external を持つ leaf `A` から親 `Processing` の `cancelGuard` 向けデータで `resume()` → `REJECTED`、状態は `A` のまま、guard 失敗カウントも増えない |
| D | 失敗時 / 永続化・restore | restore コンストラクタが状態名を葉に解決も検証もしないため、複合状態名で restore すると currentState が非葉になる | `Carta.restore(m, new FlowInstance("f1","Processing"))` → `currentState=Processing`、`isLeaf()=false`。以降 engine は葉である前提で動く |

補足（今回スコープ外として記録）: `findAutoTransition` / `findBranchTransition` は階層をバブリングしない。
`findEventTransition` はバブリングする。この非対称は `.auto("<複合状態>", ...)` を静かに死んだ定義にするが、
`build()` は検出しない。C と同種の「バブリング規則が遷移種別ごとに違う」問題として別途扱う。

## 3. 1改善の選定

**A + B を採る。両者は「auto-chain が終わらない／打ち切られたことを誰も知れない」という同一の意味単位である。**

| 候補 | 価値 | 変更の危険度 | 可逆性 | 採否 |
|---|---|---|---|---|
| A | **最大**。`build()` が祝福した**正しい定義**でも起きる。長時間 flow では中間状態が永続化され、`Carta.restore()` は auto-chain を再実行しないので恒久停止する。例外もログも残らず原因特定が定義の目視しかない | 低（エラー経路のみ。正常完了する flow は一切変わらない） | 高（1 commit revert） | **採用** |
| B | 高。A の主要な発生源であり、build 時に潰せば A の例外は「上限が本当に足りない」場合だけに絞れる。Carta の売り「build 時に無限ループを検出」が階層で崩れている点を直す | 低（既に壊れている定義のみ新たに reject） | 高 | **採用（A と同一単位）** |
| C | 高だが、バブリング意味論そのものの変更になる。現在動いている定義の挙動が変わりうる | 中 | 中 | 見送り（別 issue） |
| D | 中。誤用時の防御であり、正しく `toFlowInstance()` を使う限り起きない | 低 | 高 | 見送り（別 issue） |

「小さく安全・可逆」の条件を満たしつつ最大価値なのは A。B は A の build-time 側の対であり、
分けると「A だけ直して B の定義は runtime 例外に落ちる」という中途半端な状態になるため同じ PR に含める。

## 4. 決定（decision）

**DD-CARTA-001: auto-chain の非終端は無音であってはならない。**

1. `CartaEngine.autoChain()` は、上限 `MAX_AUTO_CHAIN_DEPTH` に達してなお実行可能な auto/branch 遷移が
   残っている場合に限り、`CartaException("AUTO_CHAIN_LIMIT", ...)` を送出する。
   メッセージには打ち切り地点の state 名・上限値・直近の遷移列を含める。
   上限に達しても続きが無い場合（terminal / external 待ち）は従来どおり無言で戻る。
2. `StateMachine.validateAutoDAG()` は auto/branch の**遷移先のみ**を `resolveToLeaf()` と同じ規則で
   葉に解決してから cycle 検出する。遷移元は engine が完全一致で引くため解決しない（偽陽性を作らない）。
   解決できない場合（未知の state、初期子の無い複合状態）は宣言名のまま扱い、V1/V2 の報告を妨げない。
3. 上限値 10 の変更・設定可能化は本決定に含めない。まず「当たったことが分かる」を成立させる。

### 契約変更としての位置づけ

上限到達時の観測可能な振る舞いは `README.md` にも `docs/spec-carta.md` にも契約として書かれていなかった。
`TramliCompatTest#autoChainStopsWithoutExceptionAtMaximumDepth`（PR #39, 2026-08-29）が現状を
characterization test として固定していたのみである。本 decision はこれを**契約の新規確定**として扱い、
テスト名と `docs/spec-carta.md` を新契約に合わせる。

挙動が変わるのは (a) 上限に達する定義、(b) 階層解決すると cycle になる定義の 2 つだけで、
いずれも**従来から既に壊れていた**（無音で途中停止していた）定義である。正常に完了していた flow、
公開型・メソッド名・`ResumeResult` の値・既存 error code は変更しない。

## 5. 受入条件

issue #40 の「受け入れ条件」1〜9 を正とする。要点は次の 4 つ。

- 上限打ち切りが `AUTO_CHAIN_LIMIT` で観測でき、メッセージから定義のどこを見ればよいか分かる
- 上限に達しない flow の挙動・log・戻り値が一切変わらない
- 階層解決後の cycle が `build()` で `INVALID_DEFINITION` になる（auto 経由・branch 経由の両方）
- 初期子の無い複合状態では V2 のエラー報告が従来どおり出る（解決処理が例外を投げない）

## 6. tramli / tramli-appspec の採否

**不採用。** 判断基準（長時間トランザクション / 外部イベント待ち / 人間介入 / 再開可能フロー）に対して:

| 基準 | 本作業（DGE 1改善の実施）での該当 |
|---|---|
| 長時間トランザクション | 該当しない。1 セッション内で完結する読解 → 決定 → 実装 → test → PR |
| 外部イベント待ち | 部分的に該当（PR 提出後に逆モデル reviewer の判断を待つ）。ただし待ちは 1 箇所・1 方向で分岐が無い |
| 人間介入 | 同上。merge / issue close は reviewer 側の 1 ステップ |
| 再開可能フロー | 該当しない。中断しても branch と issue #40 から再構成でき、専用の永続状態を持たない |

該当が「PR → review → merge」の直線的な 1 ハンドオフのみで、分岐も再開点も持たないため、
ApplicationSpec を起こす費用が回収できない。加えて環境上の事実として、`tramli-appspec`
（`https://appspec.unlaxer.org`, MCP namespace `appspec`）は volta カタログ上 `enabled: false` であり、
`appspec__appspec-authoring` skill も本 repo の context では解決されなかった。

**再検討の条件**: この repo の改善作業が (a) 複数 PR にまたがる依存関係を持つ、(b) reviewer 差し戻し →
再実装のループが 2 回以上回る、(c) セッションをまたいで中断・再開する運用になる、のいずれかになったとき。
その時点で「DGE 1 サイクル」自体を ApplicationSpec として定義する価値が出る。

なお **tramli 本体**は本 repo の設計上の起源（`README.md` 冒頭、DD-021）であり、
requires/produces とデータフロー検証はすでに全面的に採り入れられている。今回の変更もその延長で、
「build() が実行時の解決規則と同じ規則で検証する」という tramli 由来の原則に揃える方向である。
